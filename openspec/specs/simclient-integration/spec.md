# SimClient Integration

## Overview

Specifies the integration with **SimClient**, a third-party software that runs as an independent process and connects Quectel modems to the **SMSHub** marketplace for OTP/verification code sales. mp_simclient (the Orchestrator) manages SimClient's lifecycle: kills it before SIM switches, relaunches it afterward, and provides the necessary data files.

## Business Context

### Domain

SIM cards are raw material for generating **OTP/verification codes** sold through the **SMSHub** marketplace. The commercial flow is:

1. SIM registers on the cellular network (managed by mp_simclient).
2. SimClient connects the modem to the SMSHub marketplace.
3. A buyer on SMSHub requests an OTP code for a service (WhatsApp, Telegram, etc.).
4. SMSHub sends an SMS to the SIM's phone number.
5. SimClient receives the SMS via the modem and reports it to SMSHub.
6. The buyer gets their code, the operator earns revenue.

### SIM Lifecycle as Product

| State | Description | Commercial Value |
|-------|-------------|------------------|
| Virgin | New SIM, not yet activated | Maximum |
| 3M | 3 months of usage | High |
| 7M | 7 months of usage | Medium |
| Dead | Exhausted, generates no revenue | No value |

## Components

### SimClient (Third-Party Software)

- **Type**: External executable process (not internally developed).
- **Function**: Connects Quectel modems to SMSHub marketplace via serial ports.
- **Input**: `numero_simid.txt` file with phone-to-ICCID mapping.
- **Communication**: Connects directly to modem serial ports.

### Orchestrator (Lifecycle Management)

The Orchestrator in `main.py` is responsible for:

1. **Killing SimClient** before hardware operations (SIM switch, scanning).
2. **Launching SimClient** after completing switches and reboots.
3. **Providing updated data** to SimClient (numero_simid.txt).

## Operations

### kill_simclient()

Implemented in `SimController` (`hardware_controller.py`):

1. Search for SimClient process by name.
2. Send termination signal.
3. Wait for termination confirmation.
4. Verify that serial ports are free.

**Called in:**
- Start of each production round.
- Before hardware scans.
- Before mass switch operations.

### SimClient Launch

After completing the barrier pattern (all SIM switches completed):

1. Generate/update `numero_simid.txt` with currently active SIMs.
2. Launch SimClient as a separate process.
3. SimClient connects to the modems and begins listening for SMS.

### Data File: numero_simid.txt

File generated by DataManager that SimClient consumes to know which number corresponds to which SIM:

```
56912345678,8956091234567890123
56987654321,8956011234567890123
56911111111,8956031234567890123
```

**Format**: `phone_number,iccid` — one line per active SIM.

## Modem Model Detection

The system needs to detect the Quectel modem model for correct interaction:

| Model | Detection Method | Key Difference |
|-------|-----------------|----------------|
| EC25 | ATI response contains "EC25" | Reboot: CFUN=0 → CFUN=1 |
| UC20 | ATI response contains "UC20" | Reboot: CFUN=1,1 |

Detection is performed once at startup and the model is cached per port.

## Serial Port Access Coordination

An inherent access conflict exists: both mp_simclient and SimClient need access to the same modem serial ports.

### Coordination Protocol

```
Normal state:
  SimClient has exclusive access to modem ports (listening for SMS)
  mp_simclient does not touch modem ports

SIM change (new round):
  1. mp_simclient kills SimClient → frees modem ports
  2. mp_simclient opens modem ports → executes switches/reboots
  3. mp_simclient closes modem ports
  4. mp_simclient relaunches SimClient → SimClient resumes exclusive access
```

**Critical constraint**: mp_simclient and SimClient must NEVER access the same serial ports simultaneously. The kill/launch mechanism is the mutual exclusion barrier.
